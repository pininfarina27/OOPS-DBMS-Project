## 1. Project Overview — Big Picture

### What is this project?
A **Car Rental Management System** where a shop operator can:
- Add and manage cars in their fleet
- Register customers
- Rent a car to a customer
- Process the car return and calculate charges
- See rental history and business reports

### How does it work? (The 3-layer flow)

```
USER (Browser)
     ↓  types http://localhost:8080 and clicks buttons
FRONTEND (HTML + CSS + JavaScript files in web/ folder)
     ↓  sends HTTP requests like "GET /api/cars" or "POST /api/rentals"
BACKEND (Java — Main.java reads the request, calls Operations classes)
     ↓  runs SQL queries using JDBC
DATABASE (MySQL — stores all the actual data)
     ↑  returns results
BACKEND  → converts results to JSON → sends back to browser
FRONTEND → reads JSON, builds HTML table → user sees the data
```

### Why this stack?
- **Java `HttpServer`** → Built into the JDK itself, no extra software to install. Shows pure Core Java knowledge.
- **MySQL + JDBC** → Industry standard database, demonstrates real DBMS concepts.
- **Vanilla HTML/CSS/JS** → No frameworks needed, simple and easy to explain to any examiner.
- **Gson library** → Converts Java objects (like a Car object) to JSON text that the browser can read.

**Why keep Java files flat in `src/` with no sub-folders?**

**Why is there an `out/` folder?**
`javac` (the Java compiler) takes `.java` files and creates `.class` files (compiled bytecode that the JVM runs). We keep source and compiled files separate so the `src/` folder stays clean.

## 4. compile.bat and run.bat

### compile.bat
```bat
javac -cp "lib/*" -d out src/*.java
```
- `javac` → the Java compiler program
- `-cp "lib/*"` → classpath: tells the compiler where to find external JARs (Gson and MySQL connector). Without this, it won't know what `Gson` or `DriverManager` is.
- `-d out` → output directory: put all compiled `.class` files into the `out/` folder
- `src/*.java` → compile ALL `.java` files inside the `src/` folder

### run.bat
```bat
java -cp "out;lib/*" Main
```
- `java` → the Java runtime (JVM)
- `-cp "out;lib/*"` → classpath: look for classes in both the `out/` folder AND the `lib/` JARs. The semicolon `;` separates multiple paths (on Windows; Linux uses `:`)
- `Main` → the name of the class with the `main()` method — this is where execution starts

## 5. sql/schema.sql

**Purpose**: Creates the database structure (tables, columns, rules). Run this ONCE when setting up.

### Line-by-line explanation:

```sql
CREATE DATABASE IF NOT EXISTS car_rental_db;
```
Creates a database called `car_rental_db`. `IF NOT EXISTS` means: don't give an error if it already exists, just skip it.

```sql
USE car_rental_db;
```
Tells MySQL "for all the following commands, work inside this database."

```sql
DROP TABLE IF EXISTS rentals;
DROP TABLE IF EXISTS cars;
DROP TABLE IF EXISTS car_categories;
DROP TABLE IF EXISTS customers;
```
Deletes the tables if they already exist, so we can start fresh. We drop `rentals` FIRST because it has foreign keys pointing to `cars` and `customers` — you cannot drop a parent table if child tables reference it.

---

### Table 1: `car_categories`
```sql
CREATE TABLE car_categories (
    category_id INT AUTO_INCREMENT PRIMARY KEY,
    category_name VARCHAR(50) NOT NULL UNIQUE,
    description VARCHAR(200)
);
```
- `INT AUTO_INCREMENT PRIMARY KEY` → `category_id` is a number, MySQL automatically assigns 1, 2, 3... for each new row. PRIMARY KEY means it must be unique and cannot be NULL.
- `VARCHAR(50) NOT NULL UNIQUE` → a text field, max 50 characters, cannot be empty, and no two categories can have the same name.
- `VARCHAR(200)` → optional description text, up to 200 characters.

---

### Table 2: `cars`
```sql
CREATE TABLE cars (
    car_id INT AUTO_INCREMENT PRIMARY KEY,
    category_id INT,
    brand VARCHAR(50) NOT NULL,
    model VARCHAR(50) NOT NULL,
    year INT NOT NULL,
    license_plate VARCHAR(20) NOT NULL UNIQUE,
    color VARCHAR(30),
    daily_rate DECIMAL(10, 2) NOT NULL,
    status ENUM('AVAILABLE', 'RENTED', 'MAINTENANCE') DEFAULT 'AVAILABLE',
    date_added DATE DEFAULT (CURRENT_DATE),
    FOREIGN KEY (category_id) REFERENCES car_categories(category_id)
        ON DELETE SET NULL ON UPDATE CASCADE
);
```
- `category_id INT` → stores which category this car belongs to. It's a number matching `car_categories.category_id`.
- `DECIMAL(10, 2)` → for money values. 10 total digits, 2 after the decimal point. Better than `FLOAT` for money because it's exact.
- `ENUM('AVAILABLE', 'RENTED', 'MAINTENANCE')` → this column can ONLY hold one of these 3 values. MySQL rejects anything else. `DEFAULT 'AVAILABLE'` means new cars start as available.
- `DATE DEFAULT (CURRENT_DATE)` → automatically stores today's date when a car is added.
- `FOREIGN KEY (category_id) REFERENCES car_categories(category_id)` → enforces a link: the `category_id` in `cars` MUST exist in `car_categories`. This is referential integrity.
- `ON DELETE SET NULL` → if a category is deleted from `car_categories`, the car's `category_id` becomes NULL instead of being deleted.
- `ON UPDATE CASCADE` → if the `category_id` changes in `car_categories`, it automatically updates in `cars` too.

---

### Table 3: `customers`
```sql
CREATE TABLE customers (
    customer_id INT AUTO_INCREMENT PRIMARY KEY,
    first_name VARCHAR(50) NOT NULL,
    last_name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE,
    phone VARCHAR(15) NOT NULL,
    address VARCHAR(200),
    registration_date DATE DEFAULT (CURRENT_DATE)
);
```
- `email VARCHAR(100) UNIQUE` → two customers cannot share the same email address.
- `phone VARCHAR(15)` → phone as text (not INT) because some phones start with 0 or have dashes.

---

### Table 4: `rentals`
```sql
CREATE TABLE rentals (
    rental_id INT AUTO_INCREMENT PRIMARY KEY,
    car_id INT NOT NULL,
    customer_id INT NOT NULL,
    rental_date DATE NOT NULL,
    return_date DATE NOT NULL,
    actual_return_date DATE,
    total_cost DECIMAL(10, 2),
    status ENUM('ACTIVE', 'COMPLETED', 'CANCELLED') DEFAULT 'ACTIVE',
    FOREIGN KEY (car_id) REFERENCES cars(car_id)
        ON DELETE RESTRICT ON UPDATE CASCADE,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
        ON DELETE RESTRICT ON UPDATE CASCADE
);
```
- `actual_return_date DATE` → no `NOT NULL` because when a rental starts, the actual return hasn't happened yet. It's filled in when the car is returned.
- `total_cost DECIMAL(10, 2)` → also nullable at first; calculated when the car is returned.
- `ON DELETE RESTRICT` → cannot delete a car or customer if they have rental records. This protects data integrity.
- Two `FOREIGN KEY`s → `car_id` must exist in `cars`, `customer_id` must exist in `customers`. This prevents "orphan" records.

## 7. Vehicle.java

**Why this file exists**: `Vehicle` is an **abstract base class**. It defines properties that ALL vehicles share — brand, model, year. It cannot be used on its own (you cannot write `new Vehicle()` in most contexts meaningfully), but it gives a common template to child classes.

**OOP Concept demonstrated**: ABSTRACTION + INHERITANCE

```java
public abstract class Vehicle {
```
`abstract` means: this class is incomplete on purpose. It has at least one abstract method that child classes MUST implement. You cannot instantiate it directly as a standalone object (well, technically with `Vehicle()` you can but `getDetails()` would be missing its implementation).

```java
    private String brand;
    private String model;
    private int year;
```
`private` means: these fields can ONLY be accessed from inside this class. Outside code must use getters/setters. This is **ENCAPSULATION** — hiding the data and controlling access.

```java
    public Vehicle(String brand, String model, int year) {
        this.brand = brand;
        this.model = model;
        this.year = year;
    }
```
A constructor with parameters. `this.brand` refers to the field of this object; `brand` (without `this`) refers to the parameter passed in. We assign one to the other.

```java
    public Vehicle() {
    }
```
Empty constructor with no parameters. Needed because when we create Car objects from database results (e.g., `new Car()`), we don't have the values yet — we set them one by one using setters.

```java
    public String getBrand() { return brand; }
    public void setBrand(String brand) { this.brand = brand; }
```
Getter = returns the value. Setter = changes the value. These are public, so outside code can read/write the brand field through these methods. This is **ENCAPSULATION**.

```java
    public abstract String getDetails();
```
`abstract` method = has no body here. It is a **promise** that every child class MUST implement this method. If a child class forgets, the compiler gives an error. This is **ABSTRACTION** — defining what must exist without saying how.

```java
    @Override
    public String toString() {
        return brand + " " + model + " (" + year + ")";
    }
```
`@Override` means this method already exists in `Object` (the root of all Java classes) and we are replacing it with our own version. `toString()` is called automatically when you print an object: `System.out.println(car)` calls `car.toString()`. This is **POLYMORPHISM**.

## 8. Car.java

**Why this file exists**: `Car` is a specific type of Vehicle. It extends Vehicle and adds car-specific details like license plate, daily rate, status.

**OOP Concepts**: INHERITANCE, POLYMORPHISM, ENCAPSULATION

```java
public class Car extends Vehicle {
```
`extends Vehicle` means Car IS-A Vehicle. Car inherits all fields and methods from Vehicle (brand, model, year, getBrand(), etc.). This is **INHERITANCE**.

```java
    private int carId;
    private int categoryId;
    private String categoryName;   // filled from JOIN query
    private String licensePlate;
    private String color;
    private double dailyRate;
    private String status;
    private String dateAdded;
```
Car-specific fields. `categoryName` is interesting — it does NOT exist in the database `cars` table. It comes from a JOIN with `car_categories`. We store it here for convenience so the frontend can show category names.

```java
    public Car(String brand, String model, int year) {
        super(brand, model, year);
    }
```
`super(brand, model, year)` calls the parent class (Vehicle) constructor. This sets the brand, model, year fields in Vehicle. If we didn't call `super()`, Vehicle's fields would never be initialized. This is **INHERITANCE** — using the parent's constructor.

```java
    @Override
    public String getDetails() {
        return getBrand() + " " + getModel() + " (" + getYear() + ") - " +
               licensePlate + " - Rs." + dailyRate + "/day - " + status;
    }
```
`@Override` means we are implementing the `abstract` method promised in Vehicle. `getBrand()`, `getModel()`, `getYear()` are methods inherited from Vehicle. This is **POLYMORPHISM** — `Car` provides its own version of `getDetails()`.

```java
    @Override
    public String toString() {
        return "Car: " + super.toString() + " [" + licensePlate + "]";
    }
```
`super.toString()` calls Vehicle's `toString()` which returns "Maruti Swift (2023)". Then we add "Car: " at the front and license plate at the end. This is **POLYMORPHISM** — overriding a method from the parent.

## 10. Rental.java

**Why this file exists**: Represents one rental transaction — which car, which customer, what dates, what cost, what status.

**OOP Concept demonstrated**: COMPOSITION

```java
    // Rental's own data
    private int rentalId;
    private int carId;
    private int customerId;
    private String rentalDate;
    private String returnDate;
    private String actualReturnDate;
    private double totalCost;
    private String status;

    // OOP: COMPOSITION — these come from JOIN queries
    private String carBrand;
    private String carModel;
    private String licensePlate;
    private String customerName;
    private double dailyRate;
```
**Why two groups of fields?**

The first group (`rentalId`, `carId`, etc.) are directly from the `rentals` table in the database.

The second group (`carBrand`, `carModel`, `customerName`) are NOT in the `rentals` table. They come from joining the `cars` and `customers` tables. Instead of storing a full `Car` object or `Customer` object inside `Rental`, we store just the display information we need. This is **COMPOSITION** — "Rental HAS-A carBrand and HAS-A customerName", not "Rental IS-A Car".

Why not store a full Car object? Because then when Gson converts the Rental to JSON, the whole Car object (with all its fields) would be nested inside. It's cleaner to store only what we need to display.

```java
    @Override
    public String toString() {
        return "Rental #" + rentalId + ": " + customerName + " -> " +
               carBrand + " " + carModel + " [" + status + "]";
    }
```
Output example: "Rental #4: Sneha Reddy -> Mahindra XUV700 [ACTIVE]"

## 11. RentalException.java

**Why this file exists**: A custom exception for business logic errors specific to our application.

**OOP Concept**: EXCEPTION HANDLING, INHERITANCE

```java
public class RentalException extends Exception {
```
`extends Exception` means `RentalException` IS-AN `Exception`. It inherits all the error-handling behavior of Java's built-in `Exception` class. This is **INHERITANCE**.

**Why not just use `Exception` directly?**
If we `throw new Exception("Car not available")`, the caller cannot tell if it's a business logic error or a system error. With `throw new RentalException("Car not available")`, the caller can specifically `catch (RentalException e)` and handle business errors separately from system errors (like database connection failure).

```java
    public RentalException(String message) {
        super(message);
    }
```
`super(message)` passes the error message to the parent `Exception` class. `getMessage()` will return this message later.

**Where is it used?**
- `CarOperations.deleteCar()` — throws it if the car has active rentals
- `CustomerOperations.deleteCustomer()` — throws it if the customer has active rentals
- `RentalOperations.rentCar()` — throws it if car is not AVAILABLE
- `RentalOperations.returnCar()` — throws it if rental is not ACTIVE
- `Main.java` — catches it and sends a 400 error response to the browser

## 13. CarOperations.java

**Why this file exists**: All database operations related to cars in one place. Follows a consistent pattern for every method.

### The Standard Pattern (used in every method):
```java
public static ArrayList<Car> getAllCars() {
    ArrayList<Car> cars = new ArrayList<>();   // empty list to fill
    Connection conn = null;                    // will hold DB connection
    PreparedStatement stmt = null;             // will hold SQL statement
    ResultSet rs = null;                       // will hold query results

    try {
        conn = DatabaseHelper.getConnection(); // open connection
        String sql = "SELECT ...";             // write the SQL query
        stmt = conn.prepareStatement(sql);     // prepare (pre-compile) the query
        rs = stmt.executeQuery();              // run it, get results

        while (rs.next()) {                    // loop through each row
            Car car = new Car();               // create a Car object
            car.setCarId(rs.getInt("car_id")); // fill fields from row
            ...
            cars.add(car);                     // add to list
        }

    } catch (Exception e) {
        System.out.println("Error: " + e.getMessage());
        e.printStackTrace();                   // print full error details
    } finally {
        try { if (rs != null) rs.close(); } catch (Exception e) {}
        try { if (stmt != null) stmt.close(); } catch (Exception e) {}
        try { if (conn != null) conn.close(); } catch (Exception e) {}
    }
    return cars;
}
```

**Why `finally` block?**
`finally` runs regardless of whether an error happened or not. We MUST close the database resources (ResultSet, PreparedStatement, Connection) to prevent memory leaks and running out of database connections. The nested `try-catch` inside finally handles the unlikely case that closing itself fails.

**Why `PreparedStatement` instead of `Statement`?**
If we wrote: `"SELECT * FROM cars WHERE brand = '" + searchWord + "'"` and the user typed `' OR '1'='1`, it would become: `"SELECT * FROM cars WHERE brand = '' OR '1'='1'"` which returns ALL rows — a SQL injection attack. `PreparedStatement` with `?` placeholders prevents this because the driver handles the escaping automatically.

---

### `getAllCars()` — Key SQL Explained:
```java
String sql = "SELECT c.*, cc.category_name FROM cars c " +
             "LEFT JOIN car_categories cc ON c.category_id = cc.category_id " +
             "ORDER BY c.car_id";
```
- `c.*` → all columns from the `cars` table (using alias `c`)
- `cc.category_name` → also get the category name from `car_categories` (alias `cc`)
- `LEFT JOIN` → combine every car with its category. If a car has no category (NULL), it still appears in results but with NULL category_name. (vs `INNER JOIN` which would hide cars with no category)
- `ON c.category_id = cc.category_id` → the joining condition: match rows where the IDs are equal
- `ORDER BY c.car_id` → sort results by car ID in ascending order

---

### `getFilteredCars()` — Dynamic SQL Explained:
```java
String sql = "SELECT ... WHERE 1=1";
ArrayList<Object> params = new ArrayList<>();

if (search != null && !search.isEmpty()) {
    sql = sql + " AND (c.brand LIKE ? OR c.model LIKE ?)";
    params.add("%" + search + "%");
    params.add("%" + search + "%");
}
```
- `WHERE 1=1` → always true, so we can safely append `AND ...` conditions without worrying about whether it's the first condition or not.
- `LIKE ?` with `%keyword%` → `%` means "any characters". So `%Hyundai%` matches "Hyundai i20", "Old Hyundai", "Hyundai".
- We build both the SQL string AND a list of parameter values together, then set them at the end.

```java
for (int i = 0; i < params.size(); i++) {
    Object param = params.get(i);
    if (param instanceof String) {
        stmt.setString(i + 1, (String) param);
    } else if (param instanceof Integer) {
        stmt.setInt(i + 1, (Integer) param);
    }
}
```
`i + 1` because PreparedStatement parameters are 1-indexed (start at 1, not 0).

---

### `addCar()` — INSERT Explained:
```java
stmt = conn.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS);
```
`RETURN_GENERATED_KEYS` tells MySQL: after INSERT, give me back the auto-generated `car_id` value.

```java
rs = stmt.getGeneratedKeys();
if (rs.next()) {
    generatedId = rs.getInt(1);
}
```
Gets the new ID from the result. We return this ID to `Main.java` so it can include it in the response JSON `{"message": "Car added", "carId": 12}`.

### `deleteCar()` — Two-step with Exception:
```java
String checkSql = "SELECT COUNT(*) FROM rentals WHERE car_id = ? AND status = 'ACTIVE'";
...
if (rs.next() && rs.getInt(1) > 0) {
```

We check FIRST before deleting. `COUNT(*)` counts how many active rentals exist for this car. If the count > 0, we throw a `RentalException` — the car cannot be deleted while it's rented out. This is a BUSINESS RULE enforced in code.

### `rentCar()` — THE MOST IMPORTANT METHOD (TRANSACTION):
```java

        throws RentalException {
```
`throws RentalException` means: this method might throw this exception, and the caller (Main.java) MUST handle it.

```java
    // Check if car is AVAILABLE
    String checkSql = "SELECT status FROM cars WHERE car_id = ?";
    ...

```
We always check business rules BEFORE starting the transaction. If the car isn't available, we throw immediately.

```java
    // DBMS: TRANSACTION START
    conn.setAutoCommit(false);
```
`setAutoCommit(false)` means: from now on, nothing is permanently saved to the database until we call `conn.commit()`. This lets us group multiple operations together.

```java
    try {
        // Step 1: INSERT rental
        String insertSql = "INSERT INTO rentals (car_id, customer_id, rental_date, return_date, status) " +
                           "VALUES (?, ?, ?, ?, 'ACTIVE')";
        stmt = conn.prepareStatement(insertSql, Statement.RETURN_GENERATED_KEYS);
        ...
        stmt.executeUpdate();

        // Step 2: UPDATE car status
        String updateSql = "UPDATE cars SET status = 'RENTED' WHERE car_id = ?";
        ...
        stmt.executeUpdate();

        // Both succeeded — SAVE permanently
        conn.commit();
```
If BOTH steps succeed, `commit()` saves both changes permanently to the database.

```java
    } catch (Exception e) {
        // Something went wrong — UNDO everything
        conn.rollback();
        throw new RentalException("Failed to rent car: " + e.getMessage());
    }
```
If ANYTHING goes wrong (network issue, constraint violation, etc.), `rollback()` completely undoes all changes. The database stays in the state it was before we started. This is **ATOMICITY** — either everything happens or nothing happens.

**Why is this important?**
Imagine if the INSERT succeeded (rental created) but then the UPDATE failed (car still shows AVAILABLE). Then the same car could be rented to two customers at the same time! The transaction prevents this inconsistency.

```java
}
```

## 26. Common Questions Your Professor May Ask

**Q: What is the difference between `abstract class` and `interface`?**
A: An abstract class can have some methods with code and some without. It can have fields (like our `brand`, `model`, `year`). A class can only extend ONE abstract class. An interface has only method signatures (in older Java), and a class can implement MANY interfaces. We used abstract class because `Vehicle` shares actual data fields with `Car`.

**Q: What is polymorphism in your project?**
A: We have `Vehicle v = new Car("Maruti", "Swift", 2023)`. The variable `v` is of type `Vehicle`, but the actual object is a `Car`. When we call `v.getDetails()`, Java calls `Car`'s version of `getDetails()`, not Vehicle's abstract one. The method that runs depends on the ACTUAL type of the object, not the variable type.

**Q: What is a PreparedStatement and why is it better than Statement?**
A: `Statement` lets you build SQL as a string: `"SELECT * FROM cars WHERE brand = '" + input + "'"`. If `input` is `' OR '1'='1`, the SQL becomes an attack that returns all rows. `PreparedStatement` uses `?` placeholders: the user input is sent separately and MySQL treats it as pure data, never as SQL code. This prevents SQL injection.

**Q: Why did you use TRANSACTION for rent and return?**
A: Renting involves two database changes: INSERT a rental record AND UPDATE car status to RENTED. Without a transaction, if the server crashes after INSERT but before UPDATE, the rental exists but the car still shows AVAILABLE — someone could rent the same car again. With `setAutoCommit(false)` + `commit()` / `rollback()`, either BOTH changes save or NEITHER does.

**Q: What is the difference between LEFT JOIN and INNER JOIN?**
A: INNER JOIN only returns rows where both tables have a match. LEFT JOIN returns ALL rows from the left table, even if there's no match in the right table (shows NULL for missing values). We use LEFT JOIN for cars+categories (in case a car has no category set). We use INNER JOIN for rentals (we always want both the car and customer info — a rental without a car or customer shouldn't exist).

**Q: What is encapsulation?**
A: Making fields `private` so they cannot be changed from outside the class directly. Instead, we provide `public` getter and setter methods. Example: `car.brand = "BMW"` would fail (private). `car.setBrand("BMW")` works. This lets us add validation inside the setter if needed, and hides the internal structure.

**Q: What is composition?**
A: Instead of `Rental` containing a full `Car` object and a full `Customer` object, it only stores the display fields it needs (`carBrand`, `carModel`, `customerName`). Rental HAS-A car brand, HAS-A customer name. This is different from inheritance where Rental would IS-A Car (which makes no sense).

**Q: Why `HttpServer` instead of Tomcat or Spring Boot?**
A: `HttpServer` is built into the JDK itself — no extra installation, no configuration files, no XML. For a college project, it shows pure Core Java HTTP knowledge. Spring Boot would hide everything behind annotations and auto-configuration which a beginner couldn't explain.

**Q: What is COALESCE in your SQL?**
A: `COALESCE(SUM(total_cost), 0)` — if `SUM` returns NULL (because there are no completed rentals), `COALESCE` returns `0` instead. Without it, the dashboard would show "null" for revenue when there are no completed rentals.

**Q: What is `GROUP BY` and when is it used?**
A: `GROUP BY` collapses multiple rows with the same value into one row, and lets you apply aggregate functions (COUNT, SUM, AVG) to each group. Example: `GROUP BY category_name` with `SUM(total_cost)` gives one row per category with the total revenue for that category.
